# 08 A、B、C、D、E各组具体操作指南

> 文件命名：下面涉及 `A2组-`、`B2组-`、`C2组-` 的路径为第2组示例；第1组改成自己的前缀。第一次按[模板复制与命名说明](../模板/README.md)从本章 `模板-*` 原件创建副本；后续编辑已有本组副本。先查章节README，不能自行选择组号。

本教程把“职责”变成实际操作。先完成[01环境安装](01-环境安装与运行.md)，正式改文件前按[03提交教程](03-GitHub协作与提交.md)创建自己的任务分支。编辑文件不会自动上传，交付要完成commit、push和PR。

## 一、所有小组先做这六件事

### 1. 找到自己的G编号和本次任务

打开[正式章节分工表](../协作管理/章节分工表.md)，在页面按Ctrl+F（Mac用Command+F）搜索自己的G编号，注意G1也会匹配G10等，必须看完整编号。

- A/B/C是本章的角色，G编号是实际学生小组。16个ABC组各做3章，分别当一次A、B、C。
- 例如G22在第01章当A、第02章当B、第03章当C；不能把三个角色的报告都写进第一章。
- D1=G2、D2=G5、D3=G7共同整合第01—04章；E1=G10、E2=G11、E3=G16共同整合第05—08章。这六组不参加ABC轮换。
- 章节已经确定，分工表不是意向登记。发现看不懂或对应有疑问时询问助教，不自行换章。

日期统一见[进度安排](../协作管理/进度安排.md)。轮到别章并不意味着前一章不再修订。

### 2. 同角色两组分别保留自己的文件

每章A/B/C各有两个G组，按章节README对应为A1/A2、B1/B2、C1/C2。先约定重点，再从 `模板-*` 原件复制本组文件；具体步骤见[模板说明](../模板/README.md)。A1、A2可分担小节，但各自写清范围，最终由整合组汇总。B/C分别保留自己的独立证据，不能复制另一组结论当作自己验证。

一组内选本次提交同学收集修改；跨组分别建带G编号的分支。每组维护自己的Notebook，不以文件覆盖代替合并。原模板保留，后续轮换仍可复制。

### 3. 报告、Notebook和AI对话均按组分开

例如第01章G22把本组成果放在 `A2组-正文.md`、`A2组-实验.ipynb`、`A2组-编写报告.md`、`A2组-AI对话记录.md` 等文件中。G20使用A1前缀。B2、C2同理，不再在一个共享角色文件中混填两个小组。

报告注明本章组名、G编号、本组范围、日期和被审完整SHA；初稿、第1次修订、第2次修订追加在自己的文件中，保留失败与复测记录。公开只写组别。AI记录注明模型、提示词、回复、采纳、人工修改和验证；未使用就如实写未使用。

复制后将同组文件链接改到自己的副本；跨组验证写实际被审的A1/A2、B1/B2文件和SHA。Notebook重启后应按顺序运行，故意的错误案例注明预期，不以没有解释的红色异常结尾。

### 4. 建分支，先不要改文件

按03完成更新main，下面**只选自己的那条示例思路**，改成实际任务，不执行全表。表中的对应关系来自正式分工。

| 实际示例 | 分支名示例 |
| --- | --- |
| G22：第01章A | chapter-01-a-g22 |
| G22：第02章B | chapter-02-b-g22 |
| G22：第03章C | chapter-03-c-g22 |
| D1（G2）：前四章整合 | integrate-ch01-04-d1-g2 |
| E1（G10）：后四章整合 | integrate-ch05-08-e1-g10 |

命令是`git switch -c 实际分支名`，其中最后一段换成表中或自己拟定的分支名。每一轮新任务按03判断是继续原PR还是从最新main建新分支。

### 5. 第一次复制模板，之后继续本组副本

窗口A从课程根目录运行`.\course.cmd lab`（Mac/Linux用`python3.12 course.py lab`），保持打开。在浏览器左侧依次双击“教材 → 自己负责的章节”。先读章节README，按模板说明只复制本次角色的文件并重命名。每章已有4节×2学时填写栏，不复制整个模板目录。下表使用第2组示例，第1组改成实际前缀。

### 6. 填写状态要与实际一致

待填写、已完成、未运行、需修订、已复测是不同状态。模板代码只输出“未完成”时，即使不报错，也不算完成实验。每次交付写清范围和局限；没有发现错误同样要交检查证据。

## 二、A组：从初稿到修订

### A要修改哪些文件

| 本章文件 | 怎么填 |
| --- | --- |
| A2组-正文.md | 按四节填概念、假设、公式、手动核验后的推导、解释与来源 |
| A2组-实验.ipynb | 填每节输入、实现、参考值、实际输出和误差解释 |
| A2组-习题.md | 配套概念/推导、实现/数值验证、陷阱辨析三类题 |
| A2组-习题参考解答.md | 逐题对应答案、推导或运行结果与判断依据 |
| A2组-编写报告.md | 本组负责范围、人工自检、实际运行、修订与局限 |
| A2组-AI对话记录.md | 本组使用AI的具体记录与人工核验 |
| ABC共用-图片/ | 放实际用到的图片；文件名注明角色、G编号与用途 |

### A的第一次交稿，按顺序做

1. 阅读章节README与四节标题，确认三个核心概念。查指定教科书原文，记版本、页码和来源；先确定要讲的问题与条件。
2. 与同章另一A组约定范围。AI可以帮助初稿，但公式、文献、例题、代码必须自己核验。先写一节完整的小样，不要只交AI大纲。
3. 按02编辑正文和Notebook。Notebook中的每个实验应有输入、独立参考、实现、运行结果、解释；实际输出与正文引用一致。开场图注明概念示意还是实测结果。
4. 需要额外库时按05安装到本课程环境，并在正文实验说明及编写报告写出系统、设备、库版本和完整安装命令。GPU实验另给CPU可运行的小例或说明限制，不能假定每位同学都有显卡。
5. 在Notebook点 **Kernel → Restart Kernel and Run All Cells**。等待完成，逐项核对结果后Ctrl+S。失败就记录原因并修复；尚未完成内容明确保留待完成状态。
6. 编写习题与参考解答，手算或运行检查答案；再填编写报告与AI记录。两份正文/实验的同一公式、参数和结果要一致。
7. 在窗口B按03逐个git add实际修改的文件，再commit、push、创建PR。报告写本组负责的小节和实验，不能把另一A组的工作算作自己完成。
8. push成功后运行`git rev-parse HEAD`，把完整SHA和PR链接写在PR说明中，提供额外依赖及待验证项。B/C据此固定复核版本；不要只说“看main最新的”。

完成标志：PR中有本次约定内容、实验已保存的实际结果、习题与答案、编写报告和AI记录，待完成范围写清；“全章初稿完成”还需要两组内容合齐。

### A收到B/C问题以后

先读问题编号、文件/单元、预期与实测。逐条修正或用证据说明不同意见，不直接删掉B/C的原记录。在修正清单的“A回应”填写处理办法与修复SHA；新的代码或公式需重新运行或推导。请求对应B/C复测，由复核者填写结论，A不能替B/C宣称已通过。第1、2次修订各保留记录。

## 三、B组：先独立，再复现

### B要修改哪些文件

| 本章文件 | 怎么填 |
| --- | --- |
| B2组-独立推导.md | 看A实现前的人工预期、推导/参考算法及之后另一AI的补充 |
| B2组-验证.ipynb | 本组对照计算、边界测试与真实输出 |
| B2组-验证报告.md | 被审A版本、环境、步骤、预期/实测、结论与未覆盖范围 |
| B2组-修正清单.md | 问题编号、影响、证据、A回应、修复与复测记录 |
| B2组-AI对话记录.md | 另一AI的辅助过程、人工判断与限制 |

### B的操作顺序

1. 先根据章题、数学问题、假设和参考资料建立预期，暂不打开A的实现。把初始推导保存到B2组-独立推导.md，按03做一次commit保留时间与版本，再开始读A。已看过就披露范围，不补写假的独立时间。
2. 选择与A不同的AI工具或模型辅助比较，记录双方模型信息；不能使用另一模型时按角色规则与助教确认替代办法，不假称满足要求。
3. 收到A的PR链接和完整SHA后，按[06复现教程](06-B组如何在干净环境复现.md)建立**另一个课程副本和全新.venv**。先下载正确PR、固定SHA，再安装，不能直接在自己的旧环境点运行就算复现。
4. 在复现副本执行A的Notebook，比较独立预期与实测。分别记录正常情况、边界/极端情况、误差或收敛性；具体覆盖由问题决定，不机械凑数量。
5. 回自己的工作副本和B任务分支，把独立对照代码写进B2组-验证.ipynb，运行并保存。填写报告、修正清单和AI记录，记录复现副本的环境与输出。不要把复现后的A文件覆盖回主副本。
6. 发现问题时在修正清单新增唯一编号，如`CH02-G22-B001`。另一B组用自己的G编号，避免同名；已有编号继续沿用，不给同一问题反复换号。记清文件、单元标题、最小输入、独立预期、实测、容差与影响。
7. 按03提交B文件并创建PR，把报告链接与问题编号交A处理。没有发现问题时写清检查范围和方法，不填一个空的“通过”。遇到安装/运行失败也可以交“复现失败”报告。
8. A修复后取得新SHA，复测受影响的内容，并在原问题后追加新结果。涉及依赖变化时建立新复现副本/环境；最后把B报告版本和PR链接交给C。

完成标志：独立推导有先于审阅的证据，环境是新建的，报告有固定A版本与实测，五个B文件中的本组记录齐全。B负责提出和验证问题，主要内容修复由A处理。

## 四、C组：核验A和B的结论

### C要修改哪些文件

| 本章文件 | 怎么填 |
| --- | --- |
| C2组-手动推导.md | 对关键假设、边界或反例的人工推导 |
| C2组-人工复核.ipynb | 最小反例、替代方法或风险验证的代码与输出 |
| C2组-批判报告.md | 分别审过哪些A/B版本、核验结果、改进建议与局限 |
| C2组-AI陷阱.md | 原始AI主张、条件、人工证据、结论和复测 |
| C2组-AI对话记录.md | 候选漏洞与反例的来源、人工核验过程 |

### C的操作顺序

1. 取得A内容SHA和B报告/验证代码SHA，两者通常不同，报告分两栏写。可以先审A，但B尚未交报告时必须写“B部分待复核”，不能声称已经检查AB。
2. 按06的固定版本方法查看/运行A；审B使用另一个副本和B自己的PR及SHA。C正式报告、推导和代码写在自己的C任务分支。
3. 人工读核心假设、推导、算法适用条件和B的参考依据。与另一C组商定重点，例如边界条件、病态问题与稳定性混淆、训练/测试数据泄漏、比较是否公平。
4. 让AI找漏洞只能得到“候选线索”。人工推导关键步骤，查原文或可信基准，并设计能实际运行的最小例子；记录代码是手写还是AI辅助以及人工修改。
5. 在C2组-人工复核.ipynb执行反例并保存，比较预期与实测。反例不成立时写“已排除”及原因，条件不足时写“暂不能判断”，不要硬写成AI错误。
6. 在C2组-AI陷阱.md保留真实提示词、AI原话、模型日期、正确结论与证据。编号可用`CH03-G22-T001`；人工设计的错误明确写“教学构造”，不能声称AI真的说过。无已确认陷阱时提交检查范围和已排除线索即可。
7. 批判报告同时解释A主张与B验证有无共同遗漏；至少选择相关教材或基准方法人工比较。只写“AI说这里错了”没有完成核验。
8. 提交上述C文件及必要图片，PR标明A/B两个版本，说明问题影响及具体改法。A/B修改后对新SHA复核，把处理结果追加到原问题。

完成标志：人工证据能支撑每项判断，候选与已确认问题分清，A/B范围明确，推导、代码、批判报告、陷阱和AI记录齐全。C不替A改完整教材，也不替B补写“已经验证”的结论。

## 五、D/E组：把章节整理成教材

### 谁负责哪部分

| 整合组 | 实际组别 | 共同负责范围 |
| --- | --- | --- |
| D1、D2、D3 | G2、G5、G7 | 第01—04章 |
| E1、E2、E3 | G10、G11、G16 | 第05—08章 |

这是共同统筹的章段，**没有规定D1只管第一章之类的固定细分**。三组先在任务Issue或各自PR写明这次负责的文件/小节与交接顺序。可以协商一组先统一术语、一组核对图表引用、一组整理衔接与网页效果，但最终都要留下实际贡献，不能三组重复覆盖同一批文件。

### D/E具体操作

1. 先按03更新main，再建自己的整合分支。先整理已经合并的内容；尚在A/B/C的PR里的内容记录为“待合入”，不要从网页复制半篇正文冒充已整合版本。
2. 打开所负责各章README、A1/A2的正文、实验、习题和答案；阅读B/C报告与修正清单，知道哪些结论仍未解决。正文/实验/习题是教材内容，报告是核验依据。
3. 约定共用术语、符号与编号，按小节检查重复、缺漏和前后依赖；统一标题层级、图注、引用格式和章节过渡。图片导入保留趣味性，并核对解释是否准确。
4. 编辑性修整可以在自己的分支改A文件，例如同义术语统一、图注补充、链接修复；PR明确列出这些修改。发现公式、算法、数据、实验结论有实质问题，列出位置与影响交对应A修正、B/C复核，不擅自替他们修改验证结论。
5. 汇总本章A1、A2已经确认的内容，形成 `整合-正文.md`、`整合-实验.ipynb`、`整合-习题.md`，保留小组稿和报告。把整合稿内部链接改到整合稿；Notebook逐单元合并后重新运行，不直接覆盖拼接JSON。按04教程把 `_toc.yml` 中本章三处模板路径切换为整合稿。第09章整合组尚待安排，D/E当前范围不自动扩大。
6. 文件名尽量不改。若确有协调后的改名，必须同步引用它的图片路径、正文链接和目录配置，并在PR说明。每张图片先在JupyterLab预览，再在生成的网页中看实际效果。
7. 按[04生成教程](04-生成与查看教材.md)运行build，再preview。逐章点击目录、图片、公式、实验输出与习题链接；尤其检查第04→05章的衔接，由D/E共同协调。网页生成不会替你重新执行实验，缺结果时联系A确认运行和保存情况。
8. 按03只提交实际修改的源文件，不提交`.venv`、`教材/_build`、本机日志，也不新增整合周报或审阅表。D/E的本次整合说明写进PR即可，见下方可复制格式。
9. PR合并后其他整合组更新main，继续下一批修改；如需在未合并的任务分支同步最新main，按03第9节操作。遇到冲突联系负责该文件的小组，不选择全部覆盖。

### D/E的PR这样写

```markdown
整合组/实际组别：D1 / G2（按实际修改）
本次章段：第01—04章
本次具体范围：列文件和小节，不只写“前四章”
采用的内容版本：整合开始时main的完整SHA；相关A/B/C报告链接
实际修改：逐条说明术语、编号、引用、图片、衔接等修改
网页检查：实际执行的build/preview命令、查看的页面与发现的问题
待处理事项：问题位置、对应A/B/C小组、待合入的PR或待复核版本
与其他整合组的交接：本次已整理到哪里、下一步由谁处理
```

“整合开始时main的SHA”是在更新main后、建分支前运行`git rev-parse HEAD`得到的；提交自己修改后的SHA会不同。纯格式整合没有运行数值实验就写未运行及原因，不勾选“全部实验通过”。

### 三个截止日期分别做什么

| 截止日期（2026年） | D组配合前四章 | E组配合后四章 |
| --- | --- | --- |
| 10月31日 | 汇总参考教科书完成的初稿，发现结构/术语缺漏 | 汇总内容框架，核对小节、先修关系和实验计划 |
| 11月30日 | 汇总两次修订后的材料，标清仍未解决的问题 | 汇总初稿，检查正文、实验、习题及章节衔接 |
| 12月31日 | 前四章合成连贯完整整体 | 汇总两次修订后的后四章，并与前四章统一 |

日期不因整合操作改变。内容尚未完成时写清缺口和责任组，不把“页面能打开”写成“教材已验收”。

## 六、下次再打开电脑，从这里恢复工作

1. 打开课程文件夹，在地址栏输入powershell（Mac/Linux打开终端并cd到课程目录）。
2. 先运行`git status`和`git branch --show-current`，确认自己在哪个任务分支；继续原任务不必重新clone、建.venv或安装全部库。
3. 用课程助手启动JupyterLab，打开相应角色文件。每做完一段保存，需要上传时另开窗口B按03操作。
4. 若今天做新任务，先保存/提交旧任务、关闭编辑标签，再按03从更新后的main新建分支；不要带着未提交的上一章内容直接换角色。
5. 当天结束前保存，提交需要保留的版本，停止Jupyter和预览服务。PR链接、完整SHA和未完成项留在已有PR/报告里，不需要另交周报。
