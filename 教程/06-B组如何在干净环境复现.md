# 06 B组如何在干净环境复现A组实验

本教程中的B组指本章承担B角色的实际学生小组；换章后可承担A或C。每个ABC小组参与3个不同章节并分别完成过A/B/C，本章不能验证自己此前编写的内容。

“独立运行”包含两件事：在干净内核中顺序运行，以及在新建环境中验证依赖是否完整。只点击Restart Kernel完成了前者；本教程用新的课程副本和 `.venv` 完成后者，不要求初学者安装Docker。

先完成[基础安装教程](01-环境安装与运行.md)。以下以Windows第一章为例；在新的空闲PowerShell中操作，原来的Jupyter窗口可以保留，先保存有关文件。

这里的“第一章”只是复现操作示例，换章时替换目录名和打开的章节，不改变正式分工。B组完整交付文件见[08操作指南](08-各组具体操作指南.md)。

| 副本 | 用途 | 正式报告写在哪里 |
| --- | --- | --- |
| 原来的course-2026 | 自己的B或C工作分支，编辑独立验证代码与报告 | 写这里，按03提交PR |
| 新的course-review-ch01 | 固定A的某一版本，安装新环境、运行A代码 | 只保留当地复现记录，不在这里提交正式报告 |

两份副本各有自己的`.venv`和Jupyter服务，操作前先核对终端目录与浏览器端口。复制同学的`.venv`不属于新建环境。

## 1. 先保存独立推导，再打开A的实现
根据助教给出的题目、假设和参考资料，在自己的工作副本填写 `B组-独立推导.md`：先记录人工初始推导与预期，再记录另一AI的补充。保存commit或时间证据，之后才查看A组实现。若提前看过，披露看过的范围，不伪造“盲审”。

## 2. 得到被审版本
让A组提供已推送到GitHub的完整commit SHA。它确定的是某一版内容；不要只写“最新版”。尚未推送的本地commit，B组不能从远程克隆得到。

还要拿到**课程仓库中的A组PR链接或编号**、本次审查的小节、附加依赖说明。PR网址末尾`/pull/123`里的123是PR编号，和G组号、章节号、40位SHA都不同。A在自己的任务分支运行`git rev-parse HEAD`取得SHA，push成功后交给B；两组A有不同PR时分别复核并记录范围，不能用其中一个编号声称审过另一个组。

## 3. 在父目录建立新的复现副本
先保存自己的工作副本。按Win键搜索PowerShell，新开一个空闲窗口。按01默认位置安装的同学输入下行进入两个课程副本共同的父目录；实际位置不同就用自己的父目录：

```powershell
Set-Location "$env:USERPROFILE\course-work"
```

这里应是`course-work`，不是原来的`course-2026`子目录。然后运行：

```powershell
git clone https://github.com/prince19992516/-2026.git course-review-ch01
```

等待结束再输入：

```powershell
cd course-review-ch01
```

这个目录名字只是第一章示例；如果已经存在，选择新的名字，例如course-review-ch01-round2，不覆盖旧复现证据。

**先下载对应PR，再切换SHA。** 下行123必须换成A提供的、位于课程仓库的真实PR编号，不是照抄123：

```powershell
git fetch origin pull/123/head
```

这一步适用于尚未合并、包括来自Fork的PR；这里只下载，不修改当前文件。若A的指定版本已在课程main中，可以直接执行下方固定SHA步骤。找不到PR时核对编号、PR所属仓库和`git remote -v`，不要改用另一个版本蒙混过去。[GitHub本地获取PR说明](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/checking-out-pull-requests-locally)

切换到固定内容版本，下行的占位词必须替换成A提供的实际SHA：

```powershell
git switch --detach 完整commitSHA
```

核对当前版本：

```powershell
git rev-parse HEAD
```

输出必须逐字等于被审SHA。`detached HEAD`表示当前固定在一个历史版本上，用于复现是正常的；不要在这里直接写要提交的正式报告。若已经fetch正确PR但仍找不到SHA，可能编号抄错或A改写过历史，请A/助教确认可下载的实际版本，不悄悄改成main或FETCH_HEAD代替约定SHA。

## 4. 自己安装新环境

新克隆的目录不包含别人的`.venv`。下面命令都在**新副本course-review-ch01的根目录**运行，不在原course-2026里。先运行`dir`确认能看到course.cmd，再按下面顺序操作。

创建新环境：

```powershell
py -3.12 -m venv .venv
```

核对新环境Python（应为3.12.x）：

```powershell
.\.venv\Scripts\python.exe --version
```

安装当前课程基础库，下面整条命令一次复制，等安装结束且没有ERROR才继续：

```powershell
.\.venv\Scripts\python.exe -m pip install numpy==1.26.4 scipy==1.14.1 matplotlib==3.9.2 pandas==2.2.3 sympy==1.13.3 jupyterlab==4.3.5 ipykernel==6.29.5 nbformat==5.10.4 nbclient==0.10.2 jupyter-book==1.0.4.post1 sphinx==7.4.7
```

登记这个副本的内核，单独取显示名称，方便辨认：

```powershell
.\.venv\Scripts\python.exe -m ipykernel install --sys-prefix --name python3 --display-name "Python 3 (review-ch01)"
```

`--sys-prefix`把内核登记到这个副本环境，不覆盖原课程副本。名字仅用于识别，真正运行路径在下一节检查。Windows不需要激活脚本；Mac/Linux的对应命令见本教程末尾。

依赖版本以被审内容版本的安装教程为准，必要时记录教师约定的修订版本。不要先复制A的环境，或安装A电脑上其他未登记的库来“补到能跑”，否则会漏掉依赖缺失问题。

如果A的扩展实验声明了额外依赖，按其说明自行安装并记录；若未说明必需依赖，应作为复现问题反馈。

上方命令对应当前课程基础环境。如果被审历史版本明确使用另一套版本，先按该版本教程安装并在报告注明，不能一边换了库一边宣称完全复现。缺库时先记录失败和缺失声明，再依据A的补充说明安装、重跑，并把两次结果分开记录。

## 5. 亲自运行并保留证据

在这个复现副本的终端启动JupyterLab：

```powershell
.\course.cmd lab --port 8890
```

使用不同端口便于与原工作副本区分，以终端实际输出的地址为准。依次完成：

1. 在新打开的JupyterLab左侧双击`教材`，再双击`第01章-误差的代价`和`A组-实验.ipynb`。
2. 选择 **Python 3 (review-ch01)** 内核，在一个临时代码单元运行`import sys; print(sys.executable)`，确认Python路径位于`course-review-ch01/.venv/`。记录后删除这个临时单元，再从头执行A的原有代码。
3. 点击 **Kernel → Restart Kernel and Run All Cells**，等待全部执行结束。
4. 逐项比较自己的独立预期、A的说明和实际输出，记录容差、差异、报错以及尚未运行的部分。
5. 按Ctrl+S保存该副本中的实际运行结果，作为本地复现证据；不要在这个固定历史版本的副本中直接提交正式报告。

把当前SHA、Python版本、设备、种子和实际输出记录到验证报告。需要保存依赖版本时，在此复现目录另开终端运行：

```powershell
Set-Location "$env:USERPROFILE\course-work\course-review-ch01"
```

这里按默认位置举例；用了其他副本名称就替换。然后执行：

```powershell
.\.venv\Scripts\python.exe -m pip freeze > 本机依赖快照.txt
```

结束时先保存Notebook，再到这个副本的Jupyter终端按Ctrl+C停止服务。不要把原工作目录的输出误记成新环境的结果。

出现红色Traceback时记录第一个失败单元的标题、输入、完整错误及影响，后续未运行的单元写“未运行”。为了调试修改过A代码时，记录改动前后的结果；改过后的成功不能当作原SHA本来就能通过。运行保存后的副本出现modified是正常的，SHA只标识原始受审内容，保存的输出与临时修改另外作为复现证据。

## 6. 回到自己的工作分支写报告

1. 新开空闲终端，输入`Set-Location "$env:USERPROFILE\course-work\course-2026"`回原工作副本；实际位置不同就替换路径。
2. 运行`git branch --show-current`，应显示自己的B任务分支。若不是，先查看`git status`，按03处理未提交内容后再切分支，不在detached HEAD副本里写正式报告。
3. 使用原工作副本的Jupyter页面（通常8888端口），打开对应章的B文件。若原服务已关，在原目录运行`.\course.cmd lab`启动。
4. 把自己的独立对照代码放进`B组-验证.ipynb`并运行保存。复现A的结果则写进`B组-验证报告.md`，说明来自新环境；分清“新副本运行A”和“本组验证代码”两类证据。
5. 复制必要的数值、报错片段和环境版本到报告的本组段落，注明原始文件/单元和受审SHA。需要图片时放到本章`ABC共用-图片`，取`B-G编号-用途`的名字，再用相对路径引用。
6. 填写`B组-修正清单.md`、`B组-AI对话记录.md`，保留先前的独立推导。公开材料不粘贴含姓名的绝对用户路径、token和账号信息；副本位置可写`course-review-ch01/.venv`这样的相对说明。
7. 按03逐个添加自己的B文件和必要图片，commit、push、创建PR。不要把新环境整个目录上传，也不要将复现副本中保存过的A文件覆盖回主副本。

复现失败也是有效结果：写明第一处错误、最小复现步骤及影响。A修复后，对新的内容SHA重复独立复测；涉及依赖变更时使用新的环境/副本，不覆盖原来的失败记录。

## 7. C组同时检查A和B时

C也按上面方法获取指定PR与SHA。检查A使用一个复现副本；检查B再在父目录clone为例如`course-review-ch01-b`，fetch **B的PR编号**、切换**B的SHA**，在这个副本创建自己的.venv并安装B声明的依赖。不要只切到A的版本就声称审过B。

检查B的重点文件是`B组-独立推导.md`、`B组-验证.ipynb`、`B组-验证报告.md`和修正清单；需要运行的Notebook也要固定环境与版本。可以先停止A复现服务后复用8890端口，或者用`--port 8891`，始终以实际目录、内核路径和终端地址辨认。

C的手动推导、人工复核Notebook、批判报告、陷阱和AI记录仍提交在原工作副本的C分支；报告分别列A、B两个SHA及实际核验范围。B尚未完成时写“B部分待复核”。

## 8. macOS / Linux对应操作

先打开终端，用`cd "$HOME/course-work"`进入父目录。第3节的git clone、cd、git fetch、git switch、git rev-parse命令与Windows相同，按实际副本名、PR和SHA替换。固定版本后，在**复现副本根目录**逐条运行：

```bash
python3.12 -m venv .venv
```

```bash
.venv/bin/python --version
```

```bash
.venv/bin/python -m pip install numpy==1.26.4 scipy==1.14.1 matplotlib==3.9.2 pandas==2.2.3 sympy==1.13.3 jupyterlab==4.3.5 ipykernel==6.29.5 nbformat==5.10.4 nbclient==0.10.2 jupyter-book==1.0.4.post1 sphinx==7.4.7
```

```bash
.venv/bin/python -m ipykernel install --sys-prefix --name python3 --display-name "Python 3 (review-ch01)"
```

```bash
python3.12 course.py lab --port 8890
```

浏览器操作与第5节相同。保存依赖时另开终端，先`cd "$HOME/course-work/course-review-ch01"`进入复现目录，再运行`.venv/bin/python -m pip freeze > 本机依赖快照.txt`。回原工作副本则用`cd "$HOME/course-work/course-2026"`，不要执行Windows的Set-Location。

新的虚拟环境能查出很多依赖和隐藏状态问题，但不是全新操作系统。若实验依赖系统库、GPU或外部求解器，应记录这些条件，必要时由助教安排容器或第二台设备复现。
